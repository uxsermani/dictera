D2L Brightspace · Custom HTML capabilities

Two page types
keep our design.
Everywhere else
strips it.

Brightspace lets us write our own web code inside course pages. On two specific page types that gives us near-total control of typography, colour, layout and components.

Everywhere else, the platform deletes most of it the moment the page is saved. This brief sets out where that line falls, what it means for the university, and exactly what a developer can rely on.

If you read nothing else in this brief, read this. Each answer is one sentence, in plain language, and every one is backed by a source listed at the end.

02

Where it works

Two page types keep our design.
Everywhere else strips it.

This is the most important technical fact in the brief, and the one that decides everything else. D2L states it plainly in its own documentation.

Full design control

Where our design survives

  • Content pages — the main pages of a course, where learners do most of their reading. This is where the value is.
  • Homepage widgets — the panels on a course's front page. The only way to brand what a learner sees first.

D2L describes these two as supporting complete web pages. Both accept a shared design file, so a change made centrally appears everywhere.

Text formatting only

Where it is removed on save

  • Announcements, assignment briefs, discussion prompts, quiz instructions, module descriptions, rubrics and feedback
  • The Activity Feed, which does not even offer a code view

Authors can still use headings, bold, lists, links, images and tables here. They just cannot carry our visual design into these areas.

03

Styling — the visual layer

Visual design: mostly a yes.

On the two page types above, Brightspace does not restrict what we can do visually. The browser does the work, and the browser is a normal browser. The constraints are about where the styling lives, not what it can achieve.

Supported

What we can control

  • Typography — sizes, weights, line spacing, line length
  • Colour — full palette, including accessible contrast pairings
  • Spacing and rhythm — consistent margins throughout a page
  • Layout — multi-column sections, card grids, hero panels
  • Components — cards, callouts, quotes, styled tables, buttons
  • Responsive rules — different layouts for phone, tablet and desktop
  • Focus and hover states — essential for keyboard accessibility
Constraints

What limits us

  • Styling only survives in two places. Everywhere else it is deleted on save.
  • Design files must be installed by an administrator to work across all courses, not by an author in a single course.
  • Our page sits inside Brightspace's own layout. We control the content area; we cannot change the menus, headers or app around it.
  • Custom typefaces are unproven. Not documented by D2L; needs testing in our system.
  • Files moved after courses start using them will break those courses. Where we put the design file matters permanently.
What this means in practice

Anything that should look the same in every course — the type scale, the colour palette, the spacing, the card and callout styles — belongs in one file held centrally. Anything an individual author changes should be words, images and links only. If an author has to open a code view to do their job, we have designed the templates badly.

04

Interactivity — the behaviour layer

Interactivity is an IT decision,
not an authoring one.

Two facts from D2L look contradictory and are not. Together they tell us exactly how interactive content has to be delivered here.

Fact one

Interactive code typed into the editor is deleted

D2L staff have confirmed on the record that this is deliberate, and done for safety. An author pasting interactive code will simply find it gone after saving, with no error message.

Sources 05, 06

Fact two

Interactive code installed as a file does run

D2L publishes its own interactive solution for course pages, delivered exactly this way. Its free template package also ships an empty file specifically intended for an institution to add its own interactivity.

Sources 02, 03

Why this is actually good news

Because interactive code arrives as an installed file rather than typed text, it can be written once, reviewed properly for accessibility and security, and then used by every course. Instructional designers never need to write a line of it, and the institution never has to review several hundred separate versions of the same accordion.

Supported

Expandable sections, tabbed panels, steppers and similar patterns — delivered from a central file, on the two page types that allow it.

Restricted

Anything typed into an editor. Also anything loaded from an outside website, which needs security review and may be blocked outright.

Not supported

Forms and answer boxes. There is nowhere for the answers to go, so a learner's work would be silently thrown away.

05

Hard limits

Four things no amount
of code will fix.

These are not settings we can change or budget we can spend. They are properties of the platform, and any plan has to be built around them.

Limit 01

No marks, no tracking, no completion

A custom page cannot report a score, record an attempt or tick a completion box. Anything the university needs data about must live in a Quiz, an Assignment, or an integrated tool.

Limit 02

Accessibility becomes our legal responsibility

D2L is responsible for its own platform. Everything we build inside a page is ours — including whether it works with a keyboard or a screen reader. The built-in checker will not catch these failures.

Limit 03

Ongoing maintenance, not a one-off project

Brightspace updates every month. Our templates need an owner, a test course, and a check after each release. Budgeting this as a project that finishes would be a mistake.

Limit 04

Some answers only exist in our own system

D2L publishes no full list of what code is permitted, and behaviour varies by version, configuration and permissions. A short testing exercise is a prerequisite, not an optional extra.

The risk if we do nothing

Custom code is already available to anyone who can edit a course. Without a central library, individual teams will build their own versions — each with its own look, its own accessibility gaps, and no one responsible when a platform update breaks them. The choice is not whether to allow custom HTML. It is whether it is governed.

06

What we recommend

Five steps, in order.

The research points to one approach with unusual clarity: build a small, well-governed template library, and make sure authors never have to see the code inside it.

1

Run a short validation exercise first

Half a day of testing in our own Brightspace converts most of the open questions in this brief into settled facts — including the typeface question. It is a prerequisite for any design work, and it costs almost nothing.

Owner: UX + Learning Technology
2

Start from D2L's free template package, then brand it

D2L publishes a template package that is already accessible, already mobile-friendly, and specifically designed to be customised by an institution. Building from scratch would cost months and give us less support. Several universities have taken exactly this route.

Owner: UX + Learning Technology
3

Install it centrally, at organisation level

One installation, one administrator setting, and every course has access. D2L specifically advises against installing it course by course. This single decision is what turns custom HTML from a local experiment into an institutional capability.

Owner: Brightspace administrator
4

Ship the non-interactive templates first

Page introductions, module headers, learning objectives, resource cards, callouts and summaries need no interactive code at all. They address the real problem — courses being hard to navigate — and carry almost no risk. They can go live while the wider governance conversation continues.

Owner: UX + Learning Design
5

Name an owner and a monthly check

A test course containing every template, checked against each Brightspace release, plus a named team responsible for the library. Without this, the templates degrade quietly and no one notices until a learner complains.

Owner: Learning Technology
The decision we are asking for

Approval to run the validation exercise, and agreement in principle that custom page design is delivered through one centrally governed template library rather than left to individual courses. Everything else follows from those two decisions.

How to use this as a test plan

Build one page containing every row marked Validate, save it into an HTML content topic, an assignment brief, a quiz question and a custom widget, then reopen the source and compare. That single exercise converts around twenty unknowns into settled facts, and the result becomes our own internal specification — the one D2L does not publish.
